## Migrating from Atom 4.x to Atom 5.0

Atom 5.0 has two changes you should be aware of:

1. **The minimum deployment target is now iOS 17.**
2. **Offline failures are now reported as `AtomError.connectivity` instead of `AtomError.session`.**

Atom 5.0 also introduces plugins, including an optional `ConnectivityPlugin`. Plugins are opt-in and do not change existing behavior.

If your app already targets iOS 17 and does not depend on the old offline error behavior, **there may be nothing you need to change.** Existing `Requestable` conformers, `ServiceConfiguration` call sites, and all `enqueue` and `resume` overloads remain source compatible.

### iOS 17

Atom 5.0 requires **iOS 17.0 or newer**.

If your app still supports iOS 16, stay on Atom 4.x.

### Offline errors are now `AtomError.connectivity`

Atom 5.0 adds:

```swift
case connectivity(ConnectivityError)
```

This represents a request that could not be sent because the device has no usable network path.

Previously, a request that failed with `NSURLErrorNotConnectedToInternet` was reported as `.session`. Atom 5.0 reclassifies it as `.connectivity`.

This happens automatically, whether or not you configure a plugin.

There are two ways `.connectivity` can occur:

- **Transport:** `URLSession` reports `NSURLErrorNotConnectedToInternet`. Atom reclassifies the error as `.connectivity`.
- **Gated:** A configured `ConnectivityPlugin` detects that there is no usable network path and refuses to send the request.

`ConnectivityError.reason` distinguishes the two:

```swift
.transport
.gated
```

Most applications do not need to distinguish them. Both mean the same thing from the user's perspective: **there is no usable network connection.**

### If you switch over `AtomError` exhaustively

The compiler will point you to the new case:

```swift
switch error {
case .connectivity:
    presentOfflineBanner()

case .decoder, .requestable, .response, .session, .unexpected:
    presentGenericFailure()
}
```

### If your switch has a `default`

Your code will continue to compile, but the new case will fall through to `default`.

This is worth reviewing rather than ignoring. A default branch that was written for unexpected errors may not be the right behavior for an offline device.

In particular, check for:

```swift
fatalError(...)
preconditionFailure(...)
assertionFailure(...)
```

inside `default` or `@unknown default` branches.

A `default` branch already covers the new case, so the compiler will not warn you about this. An exhaustive-looking switch with a trapping default can therefore crash when the device is offline.

### If you match on the underlying error

Code that previously looked inside `.session` for `NSURLErrorNotConnectedToInternet` will no longer match:

```swift
// Atom 4.x. No longer fires in Atom 5.0.
if case let .session(underlying) = error,
   (underlying as NSError).code == NSURLErrorNotConnectedToInternet {
    presentOfflineBanner()
}
```

Use `.connectivity` instead:

```swift
// Atom 5.0.
if case .connectivity = error {
    presentOfflineBanner()
}
```

Or, if you only need to know whether the request failed because the device is offline:

```swift
if error.isOffline {
    presentOfflineBanner()
}
```

The underlying `URLSession` error is not lost. When `ConnectivityError.reason` is `.transport`, it is available through `ConnectivityError.underlyingError`.

### Other network failures are unchanged

Only `NSURLErrorNotConnectedToInternet` is reclassified.

Timeouts, DNS failures, connections that drop mid-flight, and other transport failures continue to be reported as `.session`.

This distinction is intentional: those failures do not necessarily mean the device is offline.

## ConnectivityPlugin

Atom 5.0 introduces plugins through `ServiceConfiguration.plugins`.

The parameter defaults to an empty array:

```swift
ServiceConfiguration()
```

So existing call sites continue to work without changes, and **no plugin behavior is enabled automatically.**

To have Atom check connectivity before sending a request, opt in:

```swift
let atom = Atom(
    serviceConfiguration: ServiceConfiguration(
        plugins: [ConnectivityPlugin()]
    )
)
```

If your application already has an `NWPathMonitor` wrapper, you can reuse it by conforming it to `ConnectivityMonitoring` rather than running a second monitor:

```swift
extension AppNetworkMonitor: ConnectivityMonitoring {
    var snapshot: ConnectivitySnapshot {
        get async {
            ConnectivitySnapshot(
                status: isConnected ? .satisfied : .unsatisfied,
                interface: currentInterface,
                changedAt: lastChange
            )
        }
    }
}
```

Here `lastChange` is a stored property on your monitor. Your monitor writes it when the status flips, from satisfied to unsatisfied or back, and leaves it alone the rest of the time. Reading a snapshot must never move it. `currentInterface` is a stored property as well, written whenever the path updates, so the snapshot reports the interface the monitor is actually on instead of a fixed guess.

`changedAt` has no default value, so the compiler requires you to supply it. That closes the trap where a snapshot built without a stamp quietly carried the moment of the read. What still needs care is which moment you pass, because it has to be the moment the status was entered and not the moment the snapshot was built.

The settling window is measured from `changedAt`. A stamp that moves forward on every read restarts the window on every request, so the window never elapses and no request is ever refused.

Reporting `.unknown` is always safe because an unknown path does not gate a request.

For more information, see the [Plugins](../README.md#plugins) section of the README.

### Migration checklist

- [ ] Confirm your app supports iOS 17.
- [ ] Search for exhaustive `AtomError` switches and handle `.connectivity`.
- [ ] Search for code that checks `NSURLErrorNotConnectedToInternet` inside `.session`.
- [ ] Review `default` / `@unknown default` branches for trapping behavior.
- [ ] Decide whether your app wants to opt in to `ConnectivityPlugin`.
- [ ] If you already have an `NWPathMonitor`, consider conforming it to `ConnectivityMonitoring` instead of creating another monitor.
